# Аспект: модель данных, этап 1

Исходная версия: `d41099498c6faae9748a46ea91cd7aadd90313fb` (17.11.2026).
Неизменённая контрольная ветка: `aspect/baseline-stage1-20261117`.
Источник продуктовых решений — PROJECT.md. Этот документ описывает реализацию, не изменяет требования.

## Каноническое хранение

`model.js` хранит один JSON-документ в `aspect_document_v1`:

- `schemaVersion: 1` — версия схемы, неизвестная версия отклоняется;
- `catalogs.groups` — `{id, name}`; порядок текущих шести групп сохранён;
- `catalogs.staff`, `catalogs.rooms` — `{id, name, archived}`;
- `catalogs.types` — `{id, name, color}`; текущие subject/routine/event;
- `catalogs.activities` — `{id, name, typeId, archived, color}`;
- `days[YYYY-MM-DD].entries` — единый массив уроков, режимных записей и мероприятий;
- `days[date].absences` — причины отсутствия по ID сотрудника;
- `settings` — настройки существующего интерфейса;
- `directoryMetadata` и метаданные дня — совместимость с прежними служебными полями.

Запись:

```json
{
  "id": "ex-uuid",
  "typeId": "type-subject",
  "activityId": "subject-id",
  "title": null,
  "groupIds": ["group-0"],
  "staffIds": ["teacher-uuid-1", "teacher-uuid-2"],
  "roomId": "room-id",
  "start": 540,
  "end": 580,
  "subgroup": "all",
  "event": false,
  "details": {}
}
```

Названия связанных объектов в записи не дублируются. `title` служит для свободного названия мероприятия/прежней записи вне справочника. `event` — подсказка совместимости редактора, не отдельная сущность хранения. Состав `staffIds` — точный набор назначений; удалённый сотрудник не восстанавливается по позиции в прежнем массиве. Совместное мероприятие — одна запись с несколькими `groupIds`. Подгруппы `a/b` не требуют постоянного состава учеников.

Новые ID формируются через UUID, с резервным генератором для окружений без crypto.randomUUID. Старые ID сохраняются. Уникальность старых записей проверяется в пределах даты, новые ID глобально случайные; ключ записи — дата + ID. ID каталога не пересоздаётся при переименовании. Исходные ID комнат, ранее вычисленные из имени, сохраняются как непрозрачные идентификаторы.

## Граница интерфейса

Существующий редактор пока работает с представлением `extras/events`, числовыми индексами групп и именами сотрудников. `openStorage()` — явный адаптер только семи ключей приложения; глобальное window.localStorage не подменяется. На чтении `decode()` строит это представление из ID. На записи `encode()` переводит выбранные имена в ID и валидирует связи. Имена на границе трактуются как явный выбор редактора; прежние ID не могут отменить новый выбор. Остальные служебные ключи проходят в браузерное хранилище без преобразования.

Таким образом, канонический документ единственный источник расписания; прежние массивы — временные представления в памяти. Настройки и неиспользуемые сейчас недельные шаблоны сохранены в прежнем формате. Это намеренная переходная граница; полный перевод всех редакторов на ID и CRUD типов/групп относится к последующим этапам.

## Сохранение и перенос существующих данных

При первом запуске читаются прежние семь ключей, документ преобразуется и проверяется, затем записывается одним setItem. Старые ключи остаются как аварийный исходный снимок, но при наличии `aspect_document_v1` больше не читаются. Автоматического сброса нет, разрешение пользователя на очистку тестовых данных не потребовалось.

Каждая запись через адаптер сначала готовит новый документ, проверяет даты, уникальность ID, ссылки и интервалы. Изменение состояния в памяти происходит только после успешного setItem. Это атомарность одной записи документа, не транзакция нескольких UI-операций. Расширенное восстановление, миграции следующих версий, общий undo, конкурентные вкладки и нагрузка десяти лет здесь не реализованы.

Текущий экспорт резервной копии продолжает получать полное совместимое представление через адаптер. Это сохраняет существующий формат v20, но не означает закрытия всех замечаний аудита к экспорту/импорту. Полная очистка через существующие настройки проходит через адаптер. Для возврата старой версии приложение не умеет читать новую схему: нужен экспорт v20 или удаление нового ключа с возвратом к старому снимку, что потеряет изменения после миграции. Самостоятельно откатывать опубликованный код поверх новых данных нельзя.

## Изменения этапа 2

Актуальное описание надёжности: [STAGE2.md](STAGE2.md). Введены atomic(action), одноуровневое undo документа в памяти, собственный полный формат aspect-backup/version=1 и один писатель через Web Locks. Внутри aspect_document_v1 теперь оболочка storageVersion=1 с компактными массивами записей; model.serialize/deserialize преобразуют её в полную каноническую модель. Документы этапа 1 читаются. Экспорт старого v20 заменён новым форматом; прежний раздел о текущем экспорте описывает только этап 1. Граница атомарности теперь пользовательское действие, а не отдельный совместимый ключ.

## Изменения этапа 3

copy.js строит чистый preview/apply из канонического документа. Записи копируются с новыми ID; details.copyOrigin содержит дату и ID исходной записи для предупреждения о повторе, пользовательской истории изменений нет. applySchedule(next) записывает проверенный документ одним setItem и сохраняет один снимок отмены. Сам диалог находится вне общего перехватчика атомарных событий; атомарность и проверка права записи выполняются внутри applySchedule. Подробности и проверки — STAGE3.md.

## Изменения этапа 4

staff.js содержит чистые listAbsences/setAbsence/removeAbsence и findAssignments/previewReplacement/replace. Периоды вычисляются из дневных absences; схема версии 1 сохраняется. Строка выбора замены идентифицируется парой дата + ID записи. Предварительная проверка работает на полном предполагаемом результате выбранных замен, включая новые конфликты между ними. Результат записывается через applySchedule с одной отменой и прежней блокировкой вкладок. Кнопки отсутствий с data-staff-mutation и диалог замены выполняют прямую атомарную запись, исключённую из общего перехватчика действий. Проверки и ограничения — STAGE4.md.

## Изменения этапа 5

catalogs.js — чистые операции save/remove/usage/deletionReason для пяти канонических справочников. Удаление проверяет все days[].entries, включая прошлые и скрытые отменённые записи; для сотрудников также absences, для типов — activities[].typeId. Используемые объекты не архивируются и не переназначаются автоматически. Прежний archived сохраняется; явное восстановление лишь возвращает объект в выбор.

Редакторы справочников вызывают replace(next): одна проверка и запись документа без создания отмены справочников. Успешная правка сбрасывает прежнюю отмену расписания; отказ записи сохраняет документ и прежнюю отмену. Кнопки/поля прямой записи имеют data-catalog-mutation, исключающий вложенную legacy-транзакцию. Рабочий график сотрудника сохранён в той же карточке.

Группы и произвольные типы больше не подменяются фиксированными списками при encode. decode/encode сохраняют typeId записи и связи совместных мероприятий с названиями. Изменение типа названия обновляет typeId всех его записей одним действием. При удалении неиспользуемой группы адаптер пересчитывает временные числовые индексы, канонические groupIds расписаний остаются неизменными; cfg.home также сдвигается. Изменение цвета типа используется текущими и прошлыми карточками. Существующий индивидуальный цвет названия остаётся явным переопределением.

При наличии канонического документа стартовые seed-массивы, прежние customLists и миграции имён не служат вторым источником справочников. Это предотвращает возвращение удалённых объектов и старых названий при reload. Имена нормализуются для проверки дублей (Unicode NFKC, пробелы, регистр); пустые/служебные имена и неверные ссылки/цвета отклоняются. Версии схемы/хранилища/резервной копии не менялись; журнал справочников не добавлен.

Адреса model.js и catalogs.js в index.html версионируются (?v=stage5), чтобы браузер не сочетал новый редактор с кешированной прежней моделью. При изменении этих модулей версия должна меняться.

## Изменения этапа 6

board.js содержит чистые проекции канонических записей: раскладку интервалов по полосам, уникальные конфликты по паре записей + виду ресурса + ID, объединение занятых интервалов, вычитание их из рабочего диапазона и обзоры сотрудника/помещения. Модуль загружается до model.js и доступен как AspectModel.board; в CommonJS модель подключает тот же модуль. Хранилище и схема не изменены.

Раскладка использует компоненты пересечений с минимальным числом полос, для соседних интервалов полоса переиспользуется. Она не записывает координаты в документ. Масштаб — 1,5 CSS-пикселя на минуту, независим от даты/размера окна. Границы отображения — объединение настроенного диапазона и фактических интервалов дня. Закрепление обоих направлений работает внутри одного .scroll; угловой заголовок имеет верхний слой.

Обзоры читают канонический документ и не создают записей/отмены. Рабочие часы берутся по ID сотрудника (прежний ключ-имя читается для совместимости). Отсутствующий день графика означает «не задан», null — явно нерабочий день. Ранее не сохранённые часы 09:00–18:00 больше не предполагаются. Свободное время отсутствующего сотрудника — пустой набор; назначения при этом остаются видимыми. Для помещений используется фактическая шкала и нет исключений по части названия помещения.

Счётчик считает причины пересечения уникальных пар, а не количество карточек; разные общие ресурсы одной пары — отдельные причины. Отсутствия, незаданные ответственные/помещения и выход за график показаны отдельными предупреждениями списка. Один щелчок определяет редактор по фактическому виду записи, а не префиксу ID. Сохранение и подтверждение удаления используют прежние атомарные обработчики и отмену. Все адреса JS обновлены до ?v=stage6.

## Этап 7.1 — адаптивное представление карточек

card-layout.js — независимый модуль представления без доступа к модели/хранилищу. После построения доски он перебирает композиции строк и проверяет фактические фрагменты текста через DOM Range.getClientRects(), включая вертикальные границы и пересечение разных полей. Все композиции с полными именами проверяются до перехода к сокращениям. Поддержаны полное имя, первое слово с инициалами остальных частей и инициалы; несколько ответственных сохраняются на каждом уровне. Решение кешируется по содержимому и размерам с повторной проверкой геометрии. После загрузки шрифтов выполняется повторная проверка.

Режим Обычный сохраняет 1,5 CSS px/min и прокрутку. Весь день — временное состояние интерфейса, не настройка документа: редактор скрывается, все группы размещаются в доступной ширине, px/min рассчитывается по высоте контейнера и полному диапазону даты. ResizeObserver отслеживает только доступный контейнер; requestAnimationFrame объединяет перерасчёты. При отсутствии ResizeObserver используется window.resize. Щелчок по карточке в режиме Весь день возвращает рабочую доску и открывает тот же существующий редактор.

Типографика карточек постоянна: название 12px/700, время и помещение 9px, сотрудник 11px italic, A/B 10px. Размеры не зависят от режима, длительности или длины текста. Старая логика скрытия полей по порогам длительности больше не используется. При невозможности полного представления отображаются целые поля/слова с многоточием и общим сообщением о количестве компактных карточек. Если высота меньше строки неизменяемого шрифта, остаётся графическое многоточие; полные данные доступны по щелчку и в accessible name. Размер карточки при этом не растягивается поверх соседних записей.

Палитра, каноническая модель, назначения, конфликты, сохранение и отмена не изменены. Адреса скриптов обновлены до stage71. Требования к PDF отменены последующим решением в PROJECT.md; старый PDF-код не дорабатывался, пункт меню экспорта PDF убран. PROJECT.md синхронизирован с утверждённой версией основной ветки без новых продуктовых изменений.

## Актуализация интерфейса и справочников (18.11.2026)

**Текущие продуктовые правила (имеют приоритет над историческим описанием этапа 5 выше):** ровно три системных вида записей — «Урок», «Перерыв», «Мероприятие». В меню «+ Добавить» используются эти названия. В справочниках больше нет пункта «Типы активностей» и поиска по спискам. В справочнике названий занятий и активностей форма предлагает только `type-subject` («Урок») и `type-routine` («Перерыв»). У мероприятия свободное название, выбор названия из справочника удалён.

**Совместимость:** `catalogs.types`, `typeId` и внутренние ID `type-subject`, `type-routine`, `type-event` сохранены в модели, `catalogs.js` и прежних записях; это технический слой, а не четвёртый редактируемый справочник. Проверка `catalogs.js` отклоняет создание/изменение названия активности с типом вне `type-subject`/`type-routine`. Исторические сведения этапа 5 о произвольных типах описывают прежнюю реализацию и больше не являются продуктовым требованием.

**Ограничение:** обновление не является полной миграцией модели и не доказывает, что все старые записи соответствуют новым правилам. Полная браузерная регрессия пока не проведена.
