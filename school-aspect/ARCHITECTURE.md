# Аспект — текущая архитектура

Обновлено: 18.11.2026. Описывает техническое состояние, а не план работ. Продуктовые требования — [PROJECT.md](PROJECT.md). Исторические отчёты этапов 1–7.1 доступны через историю GitHub.

## Состав приложения

- `index.html` — интерфейс, редакторы, доска, настройки и адаптер существующих экранов.
- `model.js` — каноническая модель, сериализация, проверка данных, адаптация прежнего представления.
- `catalogs.js` — операции со справочниками, проверки связей, запреты удаления используемых записей.
- `copy.js` — предварительный расчёт и применение копирования дня/недели.
- `staff.js` — отсутствия, поиск назначений, предварительная проверка и массовые замены.
- `board.js` — раскладка пересечений, конфликты, занятость сотрудников и помещений.
- `card-layout.js` — подбор компоновки содержимого карточек по фактической геометрии текста.
- `tests/` — автоматизированные проверки. Проверки в браузере отдельно необходимы.

## Каноническая модель

Единственный источник актуального расписания — документ в локальном хранилище браузера под ключом `aspect_document_v1`. `schemaVersion: 1`; оболочка сериализации `storageVersion: 1`. Структура:

- `catalogs.groups`, `catalogs.staff`, `catalogs.rooms` — справочники с постоянными ID;
- `catalogs.types` — технический список типов, сохранённый для совместимости;
- `catalogs.activities` — общая техническая коллекция названий уроков и перерывов с `typeId`;
- `days[YYYY-MM-DD].entries` — уроки, перерывы и мероприятия в единой модели;
- `days[date].absences` — отсутствия сотрудников по ID;
- `settings` и служебные метаданные — настройки и совместимость.

У записи есть `id`, `typeId`, при необходимости `activityId`, `title`, `groupIds`, `staffIds`, `roomId`, `start`, `end`, `subgroup`, `event`, `details`. Время хранится в минутах от начала суток. Ссылки хранятся по ID, а не по именам. Совместное мероприятие — одна запись с несколькими `groupIds`; `title` допускает свободное название. ID при переименовании сохраняются.

## Три типа и пять пользовательских справочников

В интерфейсе доступны только «Урок», «Перерыв», «Мероприятие» (`type-subject`, `type-routine`, `type-event`). Отдельного редактора типов нет. Пять пунктов справочников: «Сотрудники», «Группы», «Помещения», «Уроки», «Перерывы». Для мероприятий справочника нет, название вводится в редакторе.

Пункты `subjects` и `routines` открывают общий технический редактор `catalogEditor('activities', activityFilter)`, но каждый показывает только записи своего типа; при сохранении тип задаётся разделом, поле выбора типа отсутствует. Сотрудники ведутся только в разделе «Сотрудники», включая короткое имя, должность и рабочий график. Внутренний `catalogs.types` пока не удалён из схемы: это сохранение совместимости, не разрешение произвольных типов пользователю.

`catalogs.js` запрещает создавать или изменять название активности с типом, отличным от урока/перерыва; проверяет занятость объектов в прошлых и текущих датах и не удаляет используемые записи. Исторические значения `archived` могут присутствовать.

## Сохранение и безопасность данных

`openStorage()` — адаптер между прежним представлением редакторов (включая `extras/events`, имена сотрудников и числовые индексы групп) и каноническими ID. `decode()` готовит представление для интерфейса, `encode()` валидирует связи и возвращает документ. Старые ключи миграции не должны становиться вторым источником данных при наличии `aspect_document_v1`.

Изменение расписания записывается атомарно в пределах одного пользовательского действия, с одним снимком отмены в памяти. Отмена действует до перезагрузки. Используется защита от параллельной записи через Web Locks; автоматического слияния вкладок нет. Изменения справочников не поддерживают отмену и сбрасывают предыдущую отмену расписания.

Экспорт и импорт используют полный формат `{format:"aspect-backup",version:1,document:...}`. Восстановление сначала проверяет файл, затем после подтверждения заменяет документ. Старый экспорт v20 не поддерживается. Данные хранятся в браузере конкретного устройства; очистка данных браузера может их удалить.

## Операции расписания

`copy.js`: копирование дня/недели с предпросмотром, «Заменить»/«Объединить», новыми ID и `details.copyOrigin` для предупреждений о повторе. Пустой исходный день не очищает целевой; отсутствия не копируются.

`staff.js`: периоды отсутствий выводятся из дневных отметок; выборочная массовая замена рассчитывается на предполагаемом итоговом расписании и сохраняет других назначенных сотрудников.

`board.js`: раскладка пересекающихся записей по полосам без наложения; конфликты считаются по паре записей, виду ресурса и ID; обзоры показывают занятость и свободные интервалы. Незаполненный рабочий график не превращается в условные часы 09:00–18:00.

`card-layout.js`: проверяет варианты строк через `Range.getClientRects()`, учитывает границы и пересечения полей, сначала пробует полные имена; повторно проверяет геометрию после загрузки шрифтов и при изменении размеров. Не меняет расписание.

## Доска: текущее состояние и целевой интерфейс

**Утверждённая цель:** одна доска со всеми группами и полным диапазоном даты, автоматическим масштабом и доступным по нажатию карточки редактором.

**Фактическое состояние после этапа 7.1:** в коде ещё два режима — «Обычный» с фиксированными 1,5 CSS px/min и прокруткой и «Весь день» с подгонкой по контейнеру и скрытым редактором. Это открытое расхождение; не считать двухрежимную схему окончательным требованием. Типографика карточек этапа 7.1 использует фиксированные размеры: название 12px, время/помещение 9px, сотрудник 11px italic, подгруппа 10px. Если текст физически не помещается, используются компактная компоновка/многоточие с полными данными при открытии.

PDF-экспорт не требуется; передача расписания — снимок экрана. Старые упоминания PDF в истории этапов не актуальны.

Открытые задачи: завершить переход на единую доску, проверить читаемость карточек и совместимость старых пользовательских данных после изменения справочников, провести браузерную проверку операций. Перетаскивание карточек и изменение длительности мышью не являются утверждённой обязательной функциональностью.
